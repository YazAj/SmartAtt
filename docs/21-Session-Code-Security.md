# 21. Session-Code Security

## Code Format

Sprint 3 temporary session codes are short human-readable codes intended for an Instructor to display during an active lecture. The format is configurable through `LectureSchedulingOptions` and generated by infrastructure code, not hardcoded in controllers or views.

## Random Generation

Codes are generated with a cryptographically secure random-number generator. `Random` is not used for security-sensitive code creation.

## Hashing

The plain code is hashed before persistence. Verification uses the hash, and incorrect-code checks fail without revealing the stored value. Plain codes are not stored in `LectureSession` or `LectureSessionEvent`.

## Data Protection

The active code is also protected with ASP.NET Core Data Protection so authorized server code can recover it only for controlled Instructor/Admin response paths. Data Protection keys are local runtime material and must not be committed.

## Storage

`LectureSessions` stores:

- `SessionCodeHash`
- `ProtectedSessionCode`
- `SessionCodeExpiresAtUtc`
- `SessionCodeVersion`

It does not store the plain code. `LectureSessionEvents` never store the plain code.

## Authorization And Visibility

- Instructor receives the plain code only immediately after starting or regenerating an authorized session.
- Admin can inspect code state, but Admin monitoring pages do not display the plain code.
- Student DTOs and views exclude plain code, protected code, and hash fields.
- Anonymous users and cross-role users cannot access session actions.

## Expiration, Regeneration, And Invalidation

- Codes expire at a configured time.
- Regeneration increments the code version and invalidates the previous code.
- End, cancel, force-end, and stale expiration clear active code state.
- Terminal sessions cannot be reactivated to reuse a previous code.

## Logging Restrictions

Do not log:

- Plain session codes.
- Protected session codes.
- Code hashes.
- Passwords.
- Raw biometric images.
- Face templates.
- Data Protection key material.

Lifecycle event descriptions are safe operational messages only.

## Threats And Mitigations

| Threat | Sprint 3 Mitigation |
| --- | --- |
| Student obtains code through API/view | Student models and views omit all code fields; Student active page states code is hidden. |
| Code remains usable after session close | End/cancel/expire/force-end invalidate code state. |
| Previous regenerated code remains valid | Regeneration replaces hash/protected value and increments version. |
| Plain code leaks through database | Plain code is never persisted. |
| Plain code leaks through audit events | Lifecycle events store safe descriptions only. |
| Controller bypasses business rules | Service layer enforces ownership, active resources, and transitions. |
| Concurrent state changes | Row-version checks and transactions protect state changes. |

## Future Work Before Attendance Submission

Sprint 4 should add rate limiting, lockout behavior for repeated invalid code attempts, attendance-code validation policies, event correlation for attendance submissions, and telemetry that records only safe identifiers. These are intentionally not implemented in Sprint 3.
